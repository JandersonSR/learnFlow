# 6.2 Dual write e a outbox por dentro

O caso de uso `ContratarProposta` precisa fazer duas coisas: gravar a proposta como `Contratada` no Postgres e avisar Pagamentos pelo Kafka. Parece um `SaveChanges` seguido de um `ProduceAsync`. É exatamente aí que o dinheiro some.

## O dual write, nos dois sentidos

::: previsao
Escreva o que acontece em cada ordem, quando o processo morre (OOMKilled, nó drenado) entre as duas linhas:

```csharp
// Ordem A                                   // Ordem B
await db.SaveChangesAsync(ct);               await produtor.ProduceAsync(topico, msg, ct);
await produtor.ProduceAsync(topico, msg, ct); await db.SaveChangesAsync(ct);
```
???
**Ordem A**: a proposta fica `Contratada` e o evento **nunca** é publicado. O cliente assinou, o sistema diz "contratado", e o dinheiro não sai. Ninguém percebe até o cliente ligar.

**Ordem B**: o evento sai, Pagamentos faz o PIX, e o `SaveChanges` não acontece (ou falha por concorrência otimista, ou por uma constraint). O dinheiro saiu para uma proposta que, no banco de Propostas, nem foi contratada.

Não existe ordem certa. O problema é ter **dois** sistemas sem transação entre eles: o *dual write*. Retry não resolve (na ordem A, quem faria o retry morreu); `try/catch` não resolve (o processo morto não executa o `catch`).
:::

::: conceito Outbox transacional
Em vez de publicar no Kafka, grava-se o evento numa **tabela do mesmo banco**, na **mesma transação** da mudança de estado. Um processo separado, o **relay**, lê essa tabela e publica. Ou o estado e o evento ficam gravados juntos, ou nenhum dos dois. O "publicar" deixa de ser parte da transação de negócio e vira um trabalho que pode ser repetido até dar certo.
:::

A teoria e o primeiro relay à mão estão na [lição 5.2 da Plataforma .NET](../../../plataforma-dotnet/docs/modulo-05/02-produtor.md). Aqui a gente olha a versão de produção do CreditFlow: genérica para todos os módulos, com ordem por chave, rastreio e limpeza.

## A tabela

Do DDL [`001_schema_pagamentos.sql`](https://github.com/JandersonSR/lending-plataform/blob/main/src/Modules/Pagamentos/CreditFlow.Modules.Pagamentos/Infrastructure/Persistencia/Sql/001_schema_pagamentos.sql) (o mesmo bloco existe em todo schema que publica):

```sql
CREATE TABLE pagamentos.outbox (
    id            bigint      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    evento_id     uuid        NOT NULL,      -- UNIQUE: o mesmo evento não entra duas vezes
    tipo          text        NOT NULL,
    versao        integer     NOT NULL,
    topico        text        NOT NULL,
    chave         text        NOT NULL,
    faixa         smallint    NOT NULL,      -- lição 6.3
    conteudo      jsonb       NOT NULL,
    cabecalhos    jsonb       NOT NULL,      -- traceparent da requisição que gerou o evento
    ocorrido_em   timestamptz NOT NULL,
    criada_em     timestamptz NOT NULL,
    publicada_em  timestamptz NULL,          -- NULL = pendente
    tentativas    integer     NOT NULL DEFAULT 0,
    ultimo_erro   text        NULL
);
CREATE INDEX ix_outbox_pendentes ON pagamentos.outbox (faixa, id) WHERE publicada_em IS NULL;
```

| Detalhe | Por quê |
|---|---|
| `id bigint` identity | Ordem de inserção. Para a mesma chave, é a ordem dos commits (o agregado é atualizado com concorrência otimista, então duas transações da mesma proposta não commitam "cruzadas") |
| Índice **parcial** `WHERE publicada_em IS NULL` | O relay só procura pendentes. Com milhões de linhas publicadas, o índice continua com dezenas de entradas |
| `conteudo jsonb` | Dá para investigar com SQL (`conteudo->>'propostaId'`). Custo: o jsonb normaliza o JSON (reordena chaves); se você precisasse do byte exato (assinatura), seria `text` |
| `tentativas`, `ultimo_erro` | Diagnóstico: uma linha com 300 tentativas é um alerta, não um log perdido |

## Gravando: uma linha de código

Em Pagamentos, a transação A da saga ([`AoContratoAssinado.cs`](https://github.com/JandersonSR/lending-plataform/blob/main/src/Modules/Pagamentos/CreditFlow.Modules.Pagamentos/Application/Desembolsos/AoContratoAssinado.cs)):

```csharp
var novo = Desembolso.Solicitar(Guid.CreateVersion7(), e.PropostaId, e.ClienteId, e.UsuarioId,
    e.ValorLiquidoCentavos, e.ChavePix, agora);
db.Desembolsos.Add(novo);
db.AdicionarAoOutbox(new DesembolsoSolicitado(Guid.CreateVersion7(), agora, novo.Id, novo.PropostaId,
    novo.ClienteId, novo.ValorCentavos), novo.PropostaId.ToString(), agora);
await db.SaveChangesAsync(ct); // os dois INSERTs, numa transação só
```

`AdicionarAoOutbox` ([`OutboxDbContextExtensions.cs`](https://github.com/JandersonSR/lending-plataform/blob/main/src/BuildingBlocks/CreditFlow.BuildingBlocks/Mensageria/Outbox/OutboxDbContextExtensions.cs)) **não publica nada**. Ele lê o atributo do evento (tipo, versão, tópico), serializa, calcula a faixa da chave, captura o `traceparent` da requisição atual e faz `db.Set<MensagemOutbox>().Add(...)`. Quem leva para o banco é o `SaveChanges`, que o EF Core envolve numa transação quando há mais de um comando.

::: porque Por que o EF e não um `INSERT` à mão
Porque a garantia vem de **estar no mesmo `SaveChanges`**. Um `INSERT` à mão com outra conexão, ou um `ExecuteSql` fora da transação, reintroduz o dual write por dentro do mesmo banco. Usando o `DbSet`, não há como esquecer: a linha da outbox vive e morre com o agregado no change tracker.
:::

E as tabelas vêm de uma linha no `OnModelCreating` do módulo ([`PagamentosDbContext.cs`](https://github.com/JandersonSR/lending-plataform/blob/main/src/Modules/Pagamentos/CreditFlow.Modules.Pagamentos/Infrastructure/Persistencia/PagamentosDbContext.cs)):

```csharp
modelBuilder.AplicarMensageria(Schema); // outbox, outbox_faixas, inbox no schema "pagamentos"
```

Cada módulo tem a **sua** outbox, no **seu** schema. Nada de uma outbox central: ela obrigaria a transação de Pagamentos a tocar um schema que não é dela, quebrando a fronteira do monolito modular.

## E os eventos de domínio de Propostas?

Propostas acumula eventos de domínio no agregado. O repositório ([`PropostaRepositorioEf.cs`](https://github.com/JandersonSR/lending-plataform/blob/main/src/Modules/Propostas/CreditFlow.Modules.Propostas/Infrastructure/Persistencia/PropostaRepositorioEf.cs)) traduz cada um para o evento de integração correspondente **antes** do `SaveChanges` ([`TradutorDeEventos.cs`](https://github.com/JandersonSR/lending-plataform/blob/main/src/Modules/Propostas/CreditFlow.Modules.Propostas/Infrastructure/Persistencia/TradutorDeEventos.cs)):

```csharp
MensagemOutbox? m = evento switch
{
    Dominio.ContratoAssinado e => db.AdicionarAoOutbox(new Integracao.ContratoAssinado(
        Guid.CreateVersion7(), e.OcorridoEm, e.PropostaId, e.ClienteId, e.SolicitanteId,
        e.ValorSolicitadoCentavos, e.ValorLiberadoCentavos, e.ChavePix,
        [.. e.Parcelas.Select(p => new Integracao.ParcelaDoContrato(p.Numero, p.Vencimento, p.ValorCentavos))]),
        chave, agora),
    // ... PropostaCriada, PropostaAprovada, PropostaRecusada ...
    _ => null, // fatos só internos (PropostaLiberada, ContratacaoDesfeita...) não saem do módulo
};
```

E no repositório:

```csharp
db.Propostas.Add(proposta);
var mensagens = TradutorDeEventos.GravarNaOutbox(db, proposta, _relogio.GetUtcNow());
await db.SaveChangesAsync(ct);   // proposta + linhas da outbox, um commit
proposta.LimparEventos();
```

Repare no `catch` da violação do índice "uma proposta ativa por cliente": além de soltar a proposta do change tracker, ele solta as mensagens da outbox. Senão, o próximo `SaveChanges` do mesmo `DbContext` gravaria um `PropostaCriada` de uma proposta que nunca existiu.

É a camada de tradução da lição 6.1, no único lugar onde ela pode morar: dentro da transação.

::: armadilha Publicar a partir de um `SaveChangesInterceptor` "depois do commit"
Um interceptor que publica no Kafka em `SavedChangesAsync` parece elegante: os eventos saem sozinhos. Mas é o dual write da ordem A com outra roupa. O processo pode morrer entre o commit e o publish. Interceptor pode, sim, ser usado para **gravar** a outbox (antes do commit); nunca para publicar.
:::

::: checkpoint
Responda sem olhar o código: se o `SaveChangesAsync` acima lançar `DbUpdateConcurrencyException`, o que acontece com a linha da outbox? E com o evento no Kafka?
:::

::: solucao
A transação inteira é desfeita: nem a proposta muda, nem a linha da outbox existe. No Kafka não aparece nada, porque nada foi publicado. O caso de uso relê a proposta e tenta de novo (o `RegistrarResultadoDoDesembolso` faz até 3 vezes), e só a tentativa que commitar gera evento.
:::

## O que a outbox NÃO resolve

| Garantia | A outbox dá? |
|---|---|
| Nenhum evento perdido depois do commit | **Sim** |
| Nenhum evento sem o estado correspondente | **Sim** |
| Evento publicado exatamente uma vez | **Não**: o relay pode publicar e morrer antes de marcar `publicada_em`. Próximo ciclo publica de novo |
| Latência zero | **Não**: o evento sai no próximo ciclo do relay (até 500 ms ocioso) |

A duplicata é o preço. Quem paga é o consumidor, com idempotência (lição 6.4).

## Perguntas para responder sem olhar

::: pergunta
O que é dual write e por que inverter a ordem das duas operações não resolve?
???
Escrever em dois sistemas sem transação entre eles. Banco antes do Kafka perde o evento se o processo cair no meio; Kafka antes do banco publica um fato que o banco não confirmou. Qualquer ordem tem uma janela de inconsistência.
:::

::: pergunta
Que garantia de entrega a outbox dá, e quem paga o custo dela?
???
"Pelo menos uma vez": nada se perde depois do commit, mas o relay pode publicar de novo se cair antes de marcar. Quem paga é o consumidor, que precisa ser idempotente.
:::

::: pergunta
Por que cada módulo tem sua própria outbox, e não uma central?
???
Porque a outbox precisa estar na mesma transação do agregado, e cada módulo só escreve no seu schema. Uma outbox central obrigaria transações a cruzar fronteiras de módulo.
:::
